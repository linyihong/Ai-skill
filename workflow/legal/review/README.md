# Contract Review（五階段審閱）

適用 task type `review`、`explain`、`compare`。目標不是說「這份合約有問題」，而是產出
**分級、可行動、附建議修法的審閱結果**。

```text
1. Structural Review    → 這份合約的骨架完整嗎？
      ↓
2. Clause Review        → 逐條在說什麼？（explain 停在這裡）
      ↓
3. Risk Review          → 對我方的風險是什麼？分級
      ↓
4. Missing Clause       → 該有但沒有的條款
      ↓
5. Negotiation Suggest  → 建議怎麼改、退讓順序
```

## Stage 1 — Structural Review

先看骨架，不要一開始就逐條讀。

| 檢查 | 常見缺失 |
| --- | --- |
| 當事人 | 主體全稱／登記號是否正確；簽署人權限（→ [`../due-diligence/README.md`](../due-diligence/README.md) Layer 1） |
| 標的與範圍 | 有無 SOW／規格附件；附件是否被正文納入 |
| 對價與付款 | 金額、稅、幣別、付款節點是否完整 |
| 期間 | 生效日、期間、續約機制 |
| 終止 | 有無終止條款、存續條款 |
| 責任 | 有無責任上限、間接損失處理 |
| 爭議 | 準據法 + 爭議解決是否齊備且不矛盾 |
| 附件與定義 | 定義是否被使用、附件是否存在、交叉引用是否斷裂 |
| 版本一致性 | 條號重複、內部矛盾、雙語版本不一致 |

**Structural gap 優先於 clause wording**：缺一整個條款的影響通常大於某條措辭不佳。

## Stage 2 — Clause Review

逐條解讀「這條實際上在說什麼」，特別是與字面印象不同的地方。

| 重點類型 | 要看什麼 |
| --- | --- |
| 定義條款 | 定義的實際範圍是否比直覺大／小（例如「機密資訊」「服務」「交付物」） |
| 單方權利 | 誰可以單方變更、暫停、稽核、調價 |
| 條件與前提 | 我方義務是否無條件、對方義務是否附條件 |
| 交叉引用 | 「依第 X 條」是否指向真的存在且合理的條文 |
| 例外與但書 | 例外是否把主要義務掏空 |
| 救濟限制 | 是否把某救濟設為「唯一救濟」（sole remedy） |
| 時效與期限 | 通知期、請求期、失權條款 |
| 自動效果 | 自動續約、視為同意、逾期視為通過 |

`explain` 任務在此階段結束：輸出逐條解讀，**不**做改稿建議。

## Stage 3 — Risk Review（分級）

| 級別 | 定義 |
| --- | --- |
| **Critical** | 可能導致無上限責任、失去核心資產（IP／資料）、單方被綁死、或違法 |
| **Major** | 顯著不對等、可預見的重大成本、救濟不足、可執行性有疑 |
| **Minor** | 措辭不精確、慣例偏離但影響有限、行政不便 |

每項風險必須寫：**條號 + 為什麼是風險 + 觸發情境 + 影響**。
「這條對我方不利」不算風險描述。

## Stage 4 — Missing Clause

依交易類型檢查「該有但沒有」。缺失清單來源：
[`../strategy/decision-playbooks.md`](../strategy/decision-playbooks.md) 的九個決策點。

| 常被遺漏 | 影響 |
| --- | --- |
| 責任上限 / 間接損失排除 | 風險無上限 |
| 驗收標準與驗收期 | 付款爭議 |
| IP 逐類歸屬（含第三方元件、資料、模型） | 交付物無法使用或核心資產外流 |
| 存續條款 | 終止後義務不明 |
| 資料返還／匯出與過渡協助 | 被鎖住無法轉換供應商 |
| 不可抗力具名事由 | 履約地實際風險未涵蓋 |
| 保密期間分層 | 一律永久難執行，或期限過短 |
| 轉讓與控制權變更 | 對手方被併購後義務不明 |
| 通知條款（地址／方式／生效時點） | 送達爭議 |
| 完整合約 / 修改形式 | 口頭承諾爭議 |

### 反向檢查：我方的上游權利鏈

缺漏檢查天然朝外（對方拿到什麼）。**任何「我方保證提供 X」的條款，都要反向檢查我方取得 X
的鏈路是否完整**——這個風險不在對方稿件裡，逐條審閱找不到它。

| 承諾類型 | 反向要問 |
| --- | --- |
| 交付原始碼／設計／模型／資料集 | 交付物的**製作人力組成**是什麼？受雇人／外包／協力廠商／自由接案者？ |
| 授予修改權、衍生開發權、再授權權 | 非受雇人完成的部分，**是否有書面權利約定**？多數法域「出資聘請他人完成」的預設是權利歸**受聘人**，不是出資的我方 |
| 第三方或開源元件 | 其授權條款是否允許**轉交**與**再授權**給客戶？ |
| 設備原廠技術資料 | 是否受原廠保密拘束而不得納入交付範圍？ |
| IP 不侵權保證 / indemnity | 上述任一斷點都會讓此保證無法履行 |

缺口必須在**承諾交付之前**補齊，不是在交付日處理。具體法域的權利歸屬預設由
[`../research/README.md`](../research/README.md) 查證，不憑記憶斷言。
來源：[`feedback/history/legal/common/2026-07-30_231500-verify-upstream-ip-chain-before-promising-source-delivery.md`](../../../feedback/history/legal/common/2026-07-30_231500-verify-upstream-ip-chain-before-promising-source-delivery.md)

## Stage 5 — Negotiation Suggestions

每項風險給**可用的替代文字方向與退讓順序**，不只是「建議修改」。

```markdown
| # | 條號 | 級別 | 風險 | 建議修改方向 | 退讓順序 | 若對方拒絕 |
| - | --- | --- | --- | --- | --- | --- |
```

退讓順序來自 [`../strategy/README.md`](../strategy/README.md) 的 Decision Reasoning
`Trade-offs` 欄。多輪來回時交給 [`../negotiation/README.md`](../negotiation/README.md)。

## `compare` 任務的差異

比較兩份或兩版時，Stage 1–2 改為**差異驅動**：

1. 先做結構差異（哪些條款新增／刪除／移位）。
2. 再做措辭差異（同一條款的實質變動，忽略純格式）。
3. 標出**看似小但實質重大**的變動（例如「應」改「得」、上限數字、期限天數、
   「唯一救濟」的加入）。
4. 官方範本改版比較時，優先讀官方「修正明細對照」而非自行 diff 全文
   （見 [`../reference-sources.md`](../reference-sources.md)）。

## 產出：Review Memo

```markdown
## Review Memo
- 標的: <合約名稱 / 版本 / 來源>
- Jurisdiction / Governing Law（稿內約定）: <...>
- Risk tier: <Green|Yellow|Red>
### 1 結構檢查
### 2 逐條解讀（重點條款）
### 3 風險清單
| # | 條號 | 級別 | 風險 | 觸發情境 | 影響 |
### 4 缺漏條款
| # | 應有條款 | 為什麼需要 | 缺漏的後果 |
### 5 建議修改與退讓順序
| # | 條號 | 級別 | 建議方向 | 退讓順序 | 若對方拒絕 |
### 需律師覆核的具體項目
### Disclaimer
```

## 驗證

- 五階段是否都跑過（`explain` 止於 Stage 2、`compare` 用差異驅動）？
- 每項風險是否有條號 + 觸發情境 + 影響（而非「對我方不利」）？
- 風險是否分 Critical / Major / Minor？
- 缺漏條款是否對照過九個決策點？
- 建議是否含**退讓順序**與「對方拒絕時怎麼辦」？
