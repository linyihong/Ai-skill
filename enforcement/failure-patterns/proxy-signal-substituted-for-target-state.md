# Proxy Signal Substituted For Target State（以間接訊號替代對目標狀態的直接斷言）

Status: candidate
Class: `validation-gap`

## Trigger

Agent 即將宣告某件事成立，而手上的證據**不是該事本身的狀態**，而是與它相關的另一個訊號。典型形態：

- 指令的 exit code ／ 沒有錯誤輸出
- 「相關測試套件是綠的」
- 「目前沒有任何呼叫端會觸發它」
- 註冊時讀到的設定快照
- 直覺歸因（「這麼多測試同時失敗，一定是因為我剛改的那件事」）

只要「我觀察到的」與「我要宣告的」之間隔著一層推論，就適用本 pattern。

## Failure Mode

Agent 用一個**便宜且看似相關**的訊號，替代對目標狀態的直接查詢。訊號與狀態在多數時候相關，因此這個替代長期不會被發現；失效發生在兩者脫鉤的那一次，而那一次通常正是有問題的那一次。

同一結構的常見具體形態：

| 觀察到的 | 被宣告的 | 脫鉤原因 |
| --- | --- | --- |
| 背景／管線化指令 exit 0 | 該操作成功 | exit code 屬最外層 shell，非該操作；hook 拒絕仍可 exit 0 |
| 既有測試套件轉綠 | 新加的 guard 生效 | 兩者可能因設定優先序或註冊時機而互不相干 |
| 大量測試同時失敗 | 一定是剛才那個變更造成 | 可能是另一個潛伏缺陷首次被觸發 |
| 註冊時的設定快照一致 | 執行期的設定一致 | 延後求值（config binding／options）會看到之後疊加的來源 |
| 目前沒有呼叫端會觸發 | 該路徑安全 | 防線變成「沒有人新增呼叫端」，而非結構保證 |
| 型別已實作某介面 | 它已被注入容器 | 以命名慣例掃描的自動註冊會**靜默略過**不符慣例的型別 |
| 常數／欄位已宣告 | 使用它時值已就緒 | 靜態欄位初始化依**文字順序**；宣告在使用處之後時捕獲到 null，無編譯錯誤、無警告，症狀出現在遠處 |
| 清單上列了兩項檢查 | 有兩份獨立證據 | 其中一項的實作最後一步就是呼叫另一項；兩次跑的是同一段邏輯 |
| 同類缺陷修好了一處 | 該類缺陷已消除 | 同一目錄／同一家族的其餘 surface 未被列舉，缺陷在那裡繼續存活 |
| 上游「已經回傳」某值 | 我寫下的那個值就是它 | 字串跨語言邊界產生與消費，兩側名字不同也不會有編譯錯誤 |

共同點：agent 從未查詢它真正要宣告的那個狀態。

## Risk

- 宣告「已完成／已生效／已修復」而該狀態實際不成立，且該宣告會被寫進 commit message、plan 或交接文件，成為後人採信的錯誤事實
- 防護措施看似存在實則無效，且因為「測試是綠的」而更難被質疑
- 錯誤歸因導致做出不必要的大範圍修改，同時錯過真正的原因

## Required Agent Action

**斷言目標狀態本身，不斷言它的代理訊號。**

1. **識別求值點。** 對延後求值的機制（configuration binding、DI 解析、非同步／背景指令、hook 攔截），驗證必須發生在**求值之後**，且對象是求值結果。註冊時、送出時、啟動時取的快照不算。
2. **查詢狀態，不讀回執。** 要宣告 push 成功就查 ref 狀態；要宣告資料寫入就查資料；要宣告服務可解析就解析它。
3. **新增 guard 必須有針對該 guard 的直接測試。** 「加了 guard 之後套件仍綠」不構成 guard 有效的證據 —— 那是兩件事。
4. **大量失敗時先讀單一實際錯誤再歸因。** 不以變更的時間相關性推論因果。
5. **不以「目前無人觸發」作為安全結論。** 那是現況巧合，不是結構保證；若要當作防線，必須移除該能力而非依賴無人使用。
6. **以慣例驅動的自動註冊（名稱後綴、屬性掃描）需明確驗證涵蓋。** 不符慣例的型別會靜默未註冊，且只在首次解析時才失敗。

### 呼叫形式規則（P1；敘述性提醒已證明不足）

上列六條是判斷原則。實務上 agent 即使**已經寫下並讀過**這些原則，仍會在 shell 呼叫的組裝方式上重犯 —— 因為錯誤不在推理，而在指令的最後一個 token 是誰。一次 session 內同一形態三犯、且第三次把錯誤結論寫進對使用者的回報，是本節存在的原因。故以下為形式約束，可機械檢查，不依賴當下記得原則：

1. **狀態變更與驗證指令必須是該次呼叫的最後一個命令。** 其後不得再有任何指令 —— 包含 `| tail`、`| grep`、`| head`、`; echo`、`&& echo` 之後又接別的。管線與複合命令的 exit code 屬**最後一個**命令；`git push … | tail` 的 exit 0 是 `tail` 的，`cmd > log; echo "$?"` 的 exit 0 是 `echo` 的。兩者都會讓失敗的操作看起來成功。
   - 要保留輸出：`cmd > log 2>&1`（重導向不改變 exit code），之後**另一次呼叫**再讀 log。
2. **成敗一律由 exit code 判定。** 用 `cmd && echo PASS || echo FAIL`，或讀 `$?`。**不得以「輸出裡沒有錯誤字樣」代替** —— `cmd | grep -E "error" ; echo ok` 這種寫法的 `echo ok` 無條件執行，於是失敗的建置照樣印出 ok。
3. **批次修改腳本必須逐項斷言目標變更已生效。** 以「檔案內容有變」作為成功訊號會在多目標情境下靜默漏改：同一腳本對某檔做了兩處替換，其中一處匹配失敗、另一處成功，`s != orig` 仍為真，於是腳本回報全部成功。用 `assert old in s`（或等效）逐項確認，並讓斷言失敗中止腳本。
4. **驗證與被驗證的對象必須是同一份內容。** 精確字串比對會因為格式差異（同一屬性寫成一行或多行、縮排不同）在部分檔案落空；跨多個平行實作（多 Host、多 app、多站台）的修改，必須逐一確認而非確認其中之一後推論其餘。
5. **修一類缺陷時先列舉該類的全部位置，再逐一確認。** 「平行實作」不只指多 Host —— **同一個 Host 內的同類 surface** 同樣會被漏掉。實例：同一個 commit 修了 Settings 權限頁的「還原預設」在遠端模式假成功，卻沒碰同一目錄下會員頁的同一顆按鈕，兩者相隔數行、屬同一 port 家族；缺陷在該處存活到獨立驗證才被發現。判準是能列出「這類位置共有幾處」並逐處指認，而非「我改的那處已修好」。
6. **以「上游已經提供 X」為立論的修正，必須先讀 X 的實際值。** 立論越強，未查證的代價越高：一份主張「API 已回傳可區分錯誤碼」的修正，其映射表卻寫了兩個 API 從未發出的碼名（憑猜），真正的碼反而缺漏，於是那些失敗仍落成通用訊息 —— 正是該修正宣稱要消除的問題。跨語言邊界尤其如此：字串在一側產生、在另一側消費，沒有編譯器會對帳。

## Prevention Gate

宣告任何「已生效／已完成」之前，agent 必須能回答：

- 我實際查詢的是什麼？它**就是**我要宣告的那個狀態，還是與它相關的另一個東西？
- 若兩者脫鉤，我的觀察會不會仍然是綠的？若會，這個觀察不構成證據。
- 這個機制是否延後求值？我的驗證發生在求值前還是求值後？
- 我的結論是否依賴「目前沒有人／沒有東西觸發它」？
- **這次呼叫的最後一個命令是不是我要判成敗的那個？** 若後面接了 `tail`／`grep`／`echo`，我讀到的 exit code 不是它的。
- **我是用 exit code 判定，還是用「輸出裡沒看到錯誤」判定？** 後者不成立。
- **我這次改了幾個平行實作？** 每一個都確認過了，還是確認一個就推論其餘？
- **這類缺陷在這個 repo 共有幾處？** 我列舉過了嗎，還是只修了眼前那一處？同一目錄下有沒有同類的 surface？
- **我的立論引用了上游提供的什麼？** 那些值我讀過了，還是憑印象寫的？

任一項答不出來，先取得直接證據再宣告。

## 驗證

1. 完成宣告所引用的證據，其查詢對象與宣告對象是同一件事（可從指令與其輸出直接看出）
2. 新增的 guard／validator 有針對它本身的測試，且該測試會在 guard 被移除時失敗
3. 歸因結論有單一具體錯誤訊息或狀態查詢支持，而非時間相關性
4. 若曾以代理訊號做出錯誤宣告，該更正已寫入使用者可見的回覆與相關 durable 文件，而非只在對話中帶過
5. 狀態變更／驗證指令在 transcript 中皆為該次呼叫的最後一個命令；輸出以重導向保存，另次呼叫讀取
6. 批次修改腳本含逐項斷言，且斷言失敗會中止；跨平行實作的修改逐一確認
7. 修一類缺陷時，紀錄中可指出該類位置的完整清單與逐處狀態，而非只有被修的那處
8. 引用上游值（錯誤碼、常數名、欄位名）的修正，其紀錄可指向實際讀取的來源位置
