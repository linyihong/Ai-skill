# Fix Shape Chosen From What Exists, Not The Contract（修法形狀取決於現成品而非契約）

Status: candidate
Class: `traceability-gap`

## Trigger

某處要接上一個已存在的能力：一個端點、一個服務方法、一個既有函式。手上剛好有一個**功能相近**的東西，接上它最省事。

而該處的行為在契約文件裡有明確語意 —— 步驟順序、是否立即生效、成功的定義。

## Failure Mode

Agent 選了現成品，因為它「做的是同一件事」。但現成品的語意與契約要求的語意不同，而這個差異：

- 不會有編譯錯誤
- 不會有測試失敗（既有測試測的是現成品自己的語意）
- 在功能演示時看起來完全正常

觀察到的實例：Settings 頁面的「套用建議」在契約中是**草稿→檢視→儲存**。現成的端點是 apply（直接寫入）。重用它最省事，且回應成功、畫面也會更新 —— 但同一顆按鈕在 Mock 模式仍是草稿，於是兩個模式的語意分歧，而該分歧沒有任何檢查看得見。正確做法是新增一個唯讀端點。

同型變體：

| 現成品 | 契約要求 | 差異在哪 |
| --- | --- | --- |
| 立即寫入的 apply | 填草稿待確認 | 使用者是否還能取消 |
| 回傳空集合 | 表示「無建議」 | 空集合會被當成「建議為零」而覆蓋現有設定 |
| 單一泛用錯誤碼 | 可區分的失敗原因 | 使用者能否知道該怎麼改 |
| 靜默成功的 no-op | 該操作不支援 | 按鈕看起來有效 |

## Risk

- 兩個模式／兩個路徑語意分歧，且該分歧沒有測試或閘會發現
- 使用者依「看起來成功」做出後續動作（例如以為還能取消，或以為建議已套用而未儲存）
- 事後修正需要改動已對外的行為，成本遠高於當初新增一個正確的入口

## Required Agent Action

**先讀契約定義的語意，再挑實作手段；不要從現成品反推該有什麼語意。**

1. **接上任何既有能力前，確認契約對該處行為的敘述。** 特別是：是否立即生效、可否取消、成功的定義、失敗如何呈現。
2. **語意不符時新增正確的入口，不要遷就。** 「多一個端點」通常比「兩個模式語意分歧」便宜得多，而後者的代價會落在使用者身上。
3. **警惕「空值」的雙重解讀。** 「沒有結果」與「結果是空的」在破壞性操作上是完全不同的兩件事；讀取端必須能區分，回傳端不得以空集合表達「不適用」。
4. **不支援的操作要失敗，不要靜默成功。** 只做 refresh、只回 200、只記 log 的路徑，會讓按鈕看起來有效。
5. **同一功能有多個模式（Mock／Real、本地／遠端）時，語意一致本身就是契約的一部分。** 改動一側時明確檢查另一側。

## Prevention Gate

接上既有能力之前：

- 契約怎麼描述這個行為？我讀過那一節了嗎？
- 現成品的語意與它一致嗎？差在哪一步？
- 這個差異會被任何測試或閘發現嗎？若不會，我為什麼認為它可接受？
- 另一個模式的同一顆按鈕，行為會變得不同嗎？

## 驗證

1. 實作選擇在證據文件中附帶契約依據（引用到節），而非「重用既有端點」
2. 多模式功能的語意一致性有書面確認，或有檢查涵蓋
3. 不支援的路徑以失敗表達，且該失敗有使用者可讀的訊息
4. 「無結果」與「空結果」在型別或回傳碼上可區分
