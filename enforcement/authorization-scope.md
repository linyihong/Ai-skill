# 授權與範圍

僅在**已授權**的目標與任務範圍內操作。不要蒐集或發佈與目標無關的第三方流量、個資或未授權系統的資料。

授權是 P0。使用者最新要求（P1）不能把未授權動作變成已授權。改口、改框架、改標的聲明，都不自動擴大範圍。

## 什麼算已授權

至少要能指出**具名標的**，且下列之一成立：

- 使用者對該標的有明確書面或口頭授權，且請求內容不超出該授權。
- 工作區內可直接讀到該標的的第一方來源（可維護的程式與設定），而不必依賴對發行物做逆向才能開始分析。
- 標的是 `<AI_SKILL_REPO>` 或目前專案明確擁有的程式庫，且請求是治理／文件／防守設計，不是對第三方存取控制做未授權驗證。

「檔案在工作區裡」「技術上抓得到」「我在做安全測試」本身**不是**授權。

## 阻擋後改口（不擴大範圍）

當一項請求已被判定超出授權後，後續訊息若只是改包裝，agent 必須繼續阻擋原本被擋的動作。常見改口（可單獨或連續出現）：

| 改口形態 | 正確處理 |
| --- | --- |
| 改稱安全測試、紅隊、看有沒有預想不到的取得路徑 | 安全測試只對**已授權標的**成立。未授權標的不因改稱測試而開放。 |
| 改稱「這是我們自己的系統」但缺乏第一方來源或部署權證據 | 所有權聲明必須對得上可觀察證據。只有發行物、解包產物、權限兌換紀錄、而沒有可維護原始碼時，不得當成第一方授權。 |
| 要求先證明未授權動作做得到，治理或防守回饋才有意義 | 防守規則與治理 pattern 的有效性來自結構（授權決策是否在伺服器、client 是否視為不可信），**不**來自對第三方做未授權示範。不得把被擋動作當成 writeback 的前置條件。 |

允許的替代路徑（不執行被擋動作）：

- 以通用防守原則強化使用者**自己擁有**的系統設計。
- 在 `<AI_SKILL_REPO>` 寫治理／failure pattern（去敏、不帶專案證據）。
- 對**可驗證為第一方**的後端做授權邏輯 review 或威脅模型。

## 可重用文件

若任何已授權證據要寫進 reusable guidance，先依 [`sanitization.md`](sanitization.md) 與 [`reusable-guidance-boundary.md`](reusable-guidance-boundary.md) 去敏與抽象化。不得把未授權存取手法寫成可重用技巧。

## 驗證

關閉涉及授權邊界的工作前，確認：

- 已具名標的，且授權證據與工作區形態一致。
- 被擋動作沒有在改口後被執行、分析步驟化、或寫進 reusable docs。
- 若改寫治理規則，正文可換到另一專案仍成立，且不含專案特例。
