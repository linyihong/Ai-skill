### 2026-09-04 - 機械推導的相依封包，不可展開推導規則本身

Status: validated

#### One-line Summary

用「跟著引用展開」推導每個單位的相依封包時，若把記錄各分支入口的對照表也一起展開，封包會坍縮回原本要消除的全域集合——而且數字看起來完全正常。

#### Human Explanation

把過寬的相依封包縮小，常見作法是從每個單位的入口點出發、跟著引用遞迴展開，只收真正會用到的檔案。這比手維護清單好，因為新增引用會自動被涵蓋。

陷阱在於**推導規則自己也是一個檔案**。那張「哪個單位對應哪個入口點」的對照表必然列出**所有**入口點；只要展開過程中碰到它，所有分支就會被一次拉進來，每個單位又變回全域封包。

而且它極難察覺：

- **不會報錯**。封包只是變大，行為仍然正確（過度失效是安全方向），沒有任何訊號。
- **抵達路徑通常是間接的**。對照表往往和快取／指紋機制放在同一個檔案，而各分支都會透過使用該機制的 helper 傳遞性地碰到它。直接檢查入口點看不出來。
- **只擋「作為起點」不夠**。把該檔案從展開起點排除，它仍會被傳遞抵達然後展開。必須標成終端節點：計入雜湊，但不往下追。

判斷方式很簡單：**各分支算出來的封包大小若完全相同，推導就沒有生效。** 這是最直接的訊號，而不是去讀程式碼。

#### Trigger

- 實作了 per-unit / per-lane 的相依推導，但每個單位算出來的檔案數一模一樣
- 數字比手工原型量到的大很多，且沒有明顯原因
- 把某個檔案從展開起點移除後，數字仍然不變

#### Evidence

- Tool: 封包大小的逐單位比對；引用鏈追蹤
- Sanitized excerpt: 原型階段量到三個分支分別為 68 / 82 / 13 個檔案；實作後三者皆為 145。追蹤引用鏈發現路徑為「分支入口 → 使用快取機制的 helper → 存放分支對照表的檔案 → 全部三個分支入口」。將該檔案標為終端節點（計入雜湊、不展開）後，數字回到 75 / 89 / 20，且分支之間互不含對方的閘。
- Evidence path: 具體實作與 incident 紀錄留在 `<PROJECT_ROOT>`；此處只保留一般化規則。

#### Generalized Lesson

**推導所用的對照表、註冊表或設定檔，必須是推導圖上的終端節點——計入指紋，但不作為展開來源。**

一般化的判準：任何「列出所有分支」的檔案都不能被展開，否則它會把整個分支空間注入每一個封包。這包含對照表、路由註冊表、能力清單、以及任何形式的 index。

同時要注意，只跟字面引用的推導有第二個邊界：**動態組出的路徑會無聲地掉出封包**。這是危險方向（under-invalidation），所以應以測試釘住「每個分支自己的入口點必須在自己的封包內」，讓將來改成動態路徑時會被擋下。

#### Agent Action

**應該做：**

1. 實作完 per-unit 推導後，**第一件事是印出各單位的封包大小**。全部相同就是沒生效，不要先讀程式碼找原因。
2. 數字不對時追蹤引用鏈，找出「是誰把它帶進來的」，而不是猜。
3. 把對照表／註冊表標為終端節點，並在該處寫明理由——這個決定從程式碼外觀上看不出必要性，沒有註解的話很容易被後人「順手清掉」。
4. 縮小失效範圍後，雙向驗證：改 A 分支的輸入只讓 A 失效、改 B 的只讓 B 失效。

**不應該做：**

- 不要只把該檔案從展開「起點」排除；它仍會被傳遞抵達。
- 不要用名稱啟發式（檔名含 frontend / backend 之類）分類相依關係——這是猜測，且對「共用或不明」的一大群檔案完全無效。
- 不要因為過度失效是安全方向就不驗證推導有沒有生效；沒生效等於這項工作沒做。

#### Goal / Action / Validation

- Goal: 讓每個單位的相依封包只涵蓋真正會影響它的檔案。
- Action: 從單位所屬分支的入口點機械展開；對照表等「列出所有分支」的檔案標為終端節點。
- Validation: 各分支封包大小應不同且與原型量測相符；並以「改 A 的輸入只讓 A 失效」雙向實測。

#### Applies When

- 以引用展開推導每個單位／分支的相依集合
- 推導所需的對照表與被推導的機制放在同一份程式碼中
- 分支之間會共用 helper，因而可能傳遞性地碰到對照表

#### Does Not Apply When

- 相依集合由外部宣告（例如建置系統本身提供的相依圖），不需自行推導
- 每個單位的封包本來就以獨立設定明確列出，沒有展開步驟
- 對照表與被推導的內容位於推導圖完全碰不到的地方

#### Validation

以來源事件反向驗證：標為終端節點前，三個分支封包大小相同且遠大於原型量測；標記後回到各自的預期大小，且互不含對方的閘。再以雙向注入確認該失效的仍會失效。
