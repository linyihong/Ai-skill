### 2026-09-04 - 惰性遷移若由背景批次觸發，讀取端必須自行容忍未遷移狀態

Status: validated

#### One-line Summary

由「第一次寫入」觸發的就地遷移，會在服務啟動到第一次寫入之間留下一段讀取視窗；若讀取端不容忍未遷移狀態，升級後的第一批查詢會回 5xx，而症狀會以 flaky test 的形式出現。

#### Human Explanation

就地升級舊資料結構常寫成惰性：寫入路徑在真正動到某個儲存單位前，先確保它已是新結構。這對寫入端很自然——反正要寫了，順手升級。

問題是**讀取端沒有同樣的惰性**。它直接讀新結構，而新結構要等寫入端跑過才存在。若寫入端是批次或週期性的（每 N 秒 flush 一次、累積到一定量才寫），那麼從服務開始接受請求，到第一批寫入落地為止，都是空窗期。落在空窗期的查詢會撞上「新結構還不存在」而拋例外。

放大這個問題的兩個常見設計：

- **讀取端跨多個儲存單位聚合**（多個分檔、多個分區）。只要其中一個還沒被寫入端碰過，整個查詢就失敗，而不是只少那一份資料。
- **寫入端有錯誤吞噬**（記錄失敗不該拖垮服務，所以吞例外）。這是對的，但它讓遷移失敗變得無聲，只剩讀取端在報錯，看起來像讀取端的問題。

症狀最容易被誤判的地方在測試：測試若種了舊結構然後立刻查詢，就是在跟 flush 賽跑。它會**間歇性**失敗——單獨跑會過（時序不同），整包跑偶爾掛。於是很容易被歸類成「測試不穩」而加重試或標記跳過，而真正的產品缺陷原封不動。

#### Trigger

- 剛完成需要就地資料升級的版本更新，第一批查詢回 5xx，之後就正常了
- 某個測試種了舊結構、立即查詢，且失敗是間歇性的：單獨跑必過，整包跑偶爾失敗
- 錯誤訊息是「新結構不存在」，但程式碼裡明明有建立它的邏輯

#### Evidence

- Tool: 寫入端的批次設定；讀取端的查詢路徑；測試重複執行統計
- Sanitized excerpt: 遷移只在寫入端 flush 某個儲存單位時執行，而寫入端為週期性批次；讀取端列舉全部儲存單位並直接查新結構，無存在性保護。以獨立實驗確認：只有舊結構存在時，對新結構的查詢直接拋例外，並會冒到 API 成為 5xx。原測試在整包執行下約每三次失敗一次，單獨執行必過。
- Evidence path: 具體服務與 incident 紀錄留在 `<PROJECT_ROOT>`；此處只保留一般化規則。

#### Generalized Lesson

**遷移的觸發時機必須早於、且獨立於任何會讀到它的請求。**

兩種修法，擇一或並用：

1. **把遷移提前到啟動階段**——在服務開始接受請求之前完成，且涵蓋所有既存儲存單位，不只「當前那一個」。之後新建立的單位本來就是新結構，仍可留給惰性路徑。
2. **讓讀取端容忍未遷移狀態**——查詢前檢查結構是否存在，或同時接受新舊兩種形態。

第一種在多數情況較乾淨：只有一處負責遷移，讀取端維持單純。第二種在無法保證啟動順序時（例如讀寫由不同程序負責）才是必要的。

**間歇性失敗的測試是這類缺陷的正常外觀，不是測試品質問題。**在把測試標為 flaky 之前，先問「它在跟什麼賽跑，而那個賽跑在正式環境會不會發生」。

#### Agent Action

**應該做：**

1. 看到「就地遷移」時，先找出它的觸發點，再找出所有會讀到該結構的路徑，確認兩者的時序關係。
2. 遇到間歇性失敗，先確認是「測試不穩」還是「產品有時序缺陷」：單獨跑會過而整包偶爾掛，是時序線索而非隨機噪音。
3. 把遷移移到啟動階段時，涵蓋**所有**既存儲存單位——讀取端若跨單位聚合，只遷移當前那一個仍會失敗。
4. 用一個**不觸發寫入**的測試釘住不變式：完成啟動、不發任何寫入，斷言結構已就緒。這樣才與 flush 時序無關。

**不應該做：**

- 不要用加重試、加等待或延長逾時來讓間歇性失敗消失——那會保留正式環境的空窗期。
- 不要只憑「寫入端有建立結構的程式碼」就認定讀取端安全；關鍵是它何時執行。
- 不要因為寫入端吞掉了例外就認定遷移成功；吞噬讓失敗無聲，讀取端的錯誤可能才是唯一訊號。

#### Goal / Action / Validation

- Goal: 讓資料結構升級在任何查詢到達之前完成，或讓查詢能安全地面對尚未升級的狀態。
- Action: 將遷移提前到啟動階段並涵蓋所有既存單位；或在讀取端加入存在性保護。
- Validation: 以不發任何寫入的測試斷言啟動後結構已就緒；並確認該測試在移除修正後會失敗。

#### Applies When

- 資料結構升級以就地方式進行，且由資料路徑上的某個操作觸發
- 觸發端是批次、週期性或非同步的
- 讀取端會跨多個儲存單位聚合，或不做結構存在性檢查

#### Does Not Apply When

- 升級由獨立、必經且在服務開放前完成的步驟執行（例如部署流程中的遷移工作）
- 讀寫共用同一個同步路徑，讀取必然在寫入之後
- 讀取端本來就同時支援新舊兩種形態

#### Validation

以來源事件反向驗證：把遷移移到啟動階段後，一個完全不發寫入的測試能斷言結構已就緒；移除該修正後同一測試失敗。原本間歇性失敗的測試在修正後連續多次通過，但**連續通過本身只是弱證據**——確定性的斷言才是這條 lesson 的驗證方式。
