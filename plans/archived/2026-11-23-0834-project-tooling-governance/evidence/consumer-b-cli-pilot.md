## 1. 做了什麼（Consumer B）

| 層（Role contract） | 內容 |
| --- | --- |
| Entry | 一個約 20 行的 Node 入口：解析 `gate <name>`、呼叫 Logic、傳回結束碼 |
| Logic | 一個閘執行器（依序跑步驟、結束碼傳遞、固定樣本測試安靜成功／失敗才輸出、額外參數轉傳、快取跳過） |
| Parameters | 一份宣告式清單：每個閘是有序步驟（`fixture` 固定樣本回歸／`check` 檢查）與 label |

- 7 個純「依序呼叫 Node 腳本」的驗證閘，原本各有 `.sh` + `.ps1` 兩份（14 檔、約 215 行重複邏輯），改成各一行轉呼叫；對外檔名與文件引用不變，成對規則照常成立。淨減約 176 行。
- 固定樣本測試的快取**重用既有的 attestation（git blob hash 指紋）**，沒有另造快取。指紋輸入由執行器自動算出：測試自身、它字面提到的 `check_*` 檢查器、與兩者的區域匯入閉包。
- 9 項單元測試（步驟順序、結束碼、安靜輸出、參數轉傳、命中跳過、失敗不被快取、未知閘、閉包）。

## 2. 量測（同一台機器；交錯量測，取中位數）

| 項目 | 結果 |
| --- | --- |
| 7 閘：舊版 | 85.3 s |
| 7 閘：新版、快取關閉 | 85.7 s（**無額外成本**） |
| 7 閘：新版、快取熱 | **21.5 s**（約 −75%） |
| 全部固定樣本測試（46 個）合計 | 約 519 s；單一最大者 140 s |
| 全部檢查（82 個）合計（各自行程） | 約 59 s |
| Node 空啟動／PowerShell 空啟動 | 0.09 s／0.27 s |

> 絕對秒數隨機器負載變動很大（同一組閘曾量到 60 s 與 105 s），所以結論只採同時段交錯量測的相對值。

## 3. 被推翻的假設

原假設：「53 組 wrapper 各開一個行程，合成單一行程能省大量啟動成本。」**不成立**：行程啟動只有零頭。真正的成本分布是：

1. **固定樣本回歸測試**占約 9 成時間，且輸入（檢查器＋樣本）極少變動，卻每次 commit 都重跑 → 槓桿是**輸入指紋快取**，不是合併行程。
2. 其餘（檢查本身）的時間 **約 7 成花在檔案讀取**，且大量重複（見 §4）。

## 4. 「共用 I/O」量測（回答：規則越多、一次開檔套多條規則，會不會更快）

| 指標（78 個檢查） | 數值 |
| --- | --- |
| repo 檔案讀取總次數 | 85,360 |
| 不重複的 repo 檔案 | 11,417 → **平均每檔被讀約 7.5 次** |
| 被不只一個檢查讀到的檔案 | 10,034（約 88%） |
| 檔案系統讀取占檢查總時間 | 約 70% |

對照實驗（同一批 78 個檢查、結束碼全部一致為 0）：

| 做法 | 耗時 |
| --- | --- |
| 各自行程（現況） | 約 59 s |
| 同一行程、不共用讀取 | 30～34 s |
| **同一行程、共用讀取快取（檔案只開一次）** | **13～14 s**（約 −77%） |

**含意**：

- 成本模型：現況是 `N × (走訪＋讀檔＋解析＋規則)`；共用 I/O 後是 `1 × (走訪＋讀檔＋解析) ＋ N × 規則`。**規則越多，差距越大**，前提是單條規則比讀檔便宜——Consumer B 實測成立（讀檔約 7 成）。
- 這是**共用 I/O，不是把規則寫在一起**：每條規則仍是獨立模組，保留各自的錯誤訊息與 allowlist；統一的只有「檔案清單與內容由共用 context 提供、讀一次」。
- 更進一步（未做，只是方向）：以「檔案 blob hash × 規則」為單位做增量結果快取，成本隨**改動的檔案數**而非**規則總數**成長。
- 此實驗是粗略模擬（以引數為 key 的讀取記憶、假設執行期間 repo 不變）；正式實作需要明確的失效規則與「檢查不得在同一輪寫入被別的檢查讀取的檔案」的約束。

## 5. 對契約的觀察（只記錄，不改契約；Wall 6：目前只有一個 consumer 的證據）

| # | 觀察 | 對應契約 | 建議處置 |
| --- | --- | --- | --- |
| T-B1 | §5 Governance check architecture 的「single check entry + check registry + 統一結果形狀」在 Consumer B 可用 consumer 自己的語言落地，且與「不統一 runner」不衝突 | lock-taxonomy | Phase 4 作為 Q5 的證據：runner 可以是 consumer-local，不需要共用 |
| T-B2 | 契約對鎖只問「擋什麼」（scope／forbidden／allowlist／intent），不問「跑起來多貴」。Consumer B 的鎖執行成本集中在重複讀檔與每次必跑的固定樣本回歸 | lock-taxonomy、Review Rule | 候選：Review Rule 增問「這把鎖的成本能否與同 scope 的鎖共用？」；等第二個 consumer 證據再決定 |
| T-B3 | compensating lock（成對檔案的 parity 檢查）在本試點**仍存在**：試點刻意保留 wrapper 檔名，只消除邏輯重複，沒有消除成對規則本身 | Review Rule、B2 | 真正消除需要 consumer 放寬「每個 `.sh` 都要有 `.ps1`」政策並改文件；屬 consumer 決策 |

## 6. 對 Open Questions 的影響

- **Q4**：Consumer B 的 wrapper 收斂已有一個可量測的試點；結論是「邏輯去重＋固定樣本快取」見效，「成對規則」要另案處理（T-B3）。
- **Q5**：支持維持 deferred——Consumer B 用自己的語言即可，沒有共用 runner 的需求證據。
- **Q7**：與本試點無關。
- **Q11**：此試點是 consumer 自有的收斂案例，**由 Phase 4 裁決是否計入**三案例門檻；因它是 consumer 自己的決策而非本計畫套用，建議不計為「Ai-skill 套用案例」，只計為證據。

## 7. 限制與未驗證

- 只遷移 7 個純步驟閘；含 PowerShell／bash 自有邏輯的閘（約 6 個）、需要外部指令（建置、套件、容器）的閘尚未涉及。
- 共用 I/O 只做粗略模擬，**尚未實作**；全部檢查能否在同一行程安全共跑（不互相污染）只在「結束碼一致」層級驗證。
- 快取預設在本機 pre-commit 路徑是否開啟，是 Consumer B 既有政策，本試點未更動。
- 單一機器、單一時段的量測。
